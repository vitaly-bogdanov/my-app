CI/CD это автоматизация процесса "из коммита в код до рабочего приложения в продакшне".
В любой современной компании при каждом пуше в репозиторий запускается цепочка проверок: прогоняются тесты, код проверяется линтером, собирается артефакт (обычно Docker-образ), и этот артефакт автоматически деплоится на сервер.
Без CI/CD разработка выглядит так: "выкатил релиз, через час упали тесты, ещё через день заметили, в пятницу вечером катится фикс".
С CI/CD ошибки обнаруживаются за минуты.

Понимание CI/CD требуется практически во всех Go-вакансиях.
Это часть стандартного инструментария бэкенд-разработчика.

Что означают буквы
CI (Continuous Integration, непрерывная интеграция) это автоматический запуск проверок при каждом пуше или пул-реквесте:

Код собирается (go build).
Прогоняются тесты (go test).
Запускается линтер (golangci-lint).
Запускаются проверки безопасности (govulncheck).
Если что-то упало, пул-реквест не может быть замержен.
Ты узнаёшь о проблеме сразу, а не через неделю на проде, когда из-за рефакторинга сломался редкий edge case.

CD это две разных вещи с похожими аббревиатурами:

Continuous Delivery (непрерывная поставка): после успешного CI автоматически собирается артефакт (Docker-образ) и готовится к деплою, но деплой запускает человек нажатием кнопки.
Это даёт контроль: ты хочешь выкатить в пятницу вечером?
Решаешь сам.
Continuous Deployment (непрерывное развёртывание): после успешного CI деплой происходит автоматически, без участия человека.
Быстрее, но страшнее.
Требует зрелого тестирования и хороших rollback-механизмов.
В большинстве компаний используется что-то среднее: на staging-окружение автоматический deployment, на production delivery с ручным подтверждением.

https://go-platform.itmentor.pro/uploads/course/3_web_development/cicd_pipeline.png


Общая картина: Push → Test → Lint → Build → Push image → Deploy.
Если любой шаг упал, следующие не запускаются.

Зачем это нужно
Без CI/CD типичный процесс разработки выглядит так:

Разработчик пишет код.
Локально запускает тесты, некоторые пропускает.
Коммитит, пушит.
Ревьюеры не всегда замечают косяки.
На staging кто-то ручками деплоит.
Половину шагов забывают.
На проде "вроде работает".
С CI/CD процесс детерминированный:

Разработчик коммитит.
CI сам запускает все тесты, линтеры, проверки безопасности.
Если что-то упало, PR нельзя замержить.
После мержа CD собирает артефакт и деплоит.
Все шаги задокументированы в .yml-файле, никаких "забыл сделать".
Автоматизация здесь ради воспроизводимости и отсутствия человеческих ошибок на критичных этапах.

Основные инструменты
GitLab CI/CD.
Встроен в GitLab.
Конфигурация в файле .gitlab-ci.yml в корне проекта.
Популярен в больших компаниях, особенно где GitLab используется как основной git-хостинг.

GitHub Actions.
Встроен в GitHub.
Конфигурация в .github/workflows/*.yml.
Самый популярный в open-source и стартапах.

Jenkins.
Старейшина, всё ещё встречается в больших корпорациях.
Конфигурируется через Jenkinsfile, но часто настраивается через UI.
Мощный, но старомодный.

CircleCI, TeamCity, Drone, Buildkite существуют, но встречаются реже.

Принципиальных различий между ними нет: все они запускают пайплайн (последовательность шагов) в ответ на событие (пуш, PR, тег).
Синтаксис конфигурации отличается.

Пример: GitLab CI/CD для Go-проекта
Конфигурация в файле .gitlab-ci.yml в корне проекта:

Копировать
stages:
  - test
  - build
  - deploy

test:
  stage: test
  image: golang:1.23
  script:
    - go test -race ./...
    - golangci-lint run ./...

build:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

deploy:
  stage: deploy
  script:
    - kubectl set image deployment/myapp myapp=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  only:
    - main
Разбор:

stages определяет этапы пайплайна.
Они выполняются последовательно: сначала все джобы на этапе test, потом build, потом deploy.
Если на каком-то этапе что-то упало, следующие не запускаются.
test прогоняет тесты и линтер в Go-окружении.
Флаг -race включает детектор гонок данных.
Если тест упал или линтер нашёл проблему, пайплайн падает.
build собирает Docker-образ и пушит его в registry.
$CI_REGISTRY_IMAGE и $CI_COMMIT_SHA это переменные GitLab, которые подставляются автоматически (путь к реестру и SHA текущего коммита).
deploy обновляет образ в Kubernetes через kubectl set image.
Секция only: main означает, что деплой запускается только при пушах в ветку main, а не при любом PR.
Это минимальный пример.
В реальных проектах добавляются:

Кеширование зависимостей (go mod download кешируется между запусками).
Запуск в ветках: на PR прогоняются только тесты, на main ещё и деплой.
Staging и production окружения с разными секретами.
Уведомления в Slack/Telegram при падении.
Ручное подтверждение деплоя на prod.
Пример: GitHub Actions для Go
Тот же проект через GitHub Actions:

Копировать
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.23'
      - name: Run tests
        run: go test -race ./...
      - name: Run linter
        uses: golangci/golangci-lint-action@v4

  build:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - name: Build Docker image
        run: docker build -t myapp:${{ github.sha }} .
      - name: Push to registry
        run: |
          echo ${{ secrets.REGISTRY_PASSWORD }} | docker login -u ${{ secrets.REGISTRY_USER }} --password-stdin
          docker push myapp:${{ github.sha }}
Ключевые различия от GitLab:

Пайплайн состоит из jobs (здесь: test и build).
Зависимости между ними задаются через needs.
Каждый шаг это step, шаги могут использовать готовые actions (переиспользуемые блоки, опубликованные в GitHub Marketplace).
on: описывает триггеры: пуш в main, PR, ручной запуск, по расписанию, и т.д.
Что нужно знать в начале
На первой работе от тебя не ждут, что ты с нуля напишешь сложный пайплайн.
Обычно он уже настроен.
Тебе нужно:

Читать существующий пайплайн и понимать, что в нём происходит.
Чинить падающие шаги (чаще всего: тесты упали, линтер не пропускает, что-то с Docker).
Добавлять новые шаги под нужды твоего сервиса: например, прогонять интеграционные тесты, запускать миграции, публиковать отчёт о покрытии.
Полное владение CI/CD (проектирование с нуля, оптимизация скорости, работа с секретами) приходит с опытом и больше относится к зоне ответственности DevOps-инженеров.

Задача 1. Собрать Go-приложение в GitHub Actions
Создай публичный репозиторий на GitHub с простым Go-проектом и добавь workflow, который автоматически запускает go build и go test при каждом push в ветку main.

Структура проекта:

Копировать
myapp/
  main.go
  main_test.go
  go.mod
  .github/workflows/ci.yml
Минимальный main.go:

Копировать
cat > main.go << 'EOF'
package main

import "fmt"

func Add(a, b int) int {
    return a + b
}

func main() {
    fmt.Println(Add(2, 3))
}
EOF
Минимальный main_test.go:

Копировать
cat > main_test.go << 'EOF'
package main

import "testing"

func TestAdd(t *testing.T) {
    if Add(2, 3) != 5 {
        t.Fatal("Add(2,3) должен вернуть 5")
    }
}
EOF
Файл .github/workflows/ci.yml - именно это и есть CI-пайплайн:

Копировать
mkdir -p .github/workflows
cat > .github/workflows/ci.yml << 'EOF'
name: CI

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'

      - name: Build
        run: go build ./...

      - name: Test
        run: go test ./...
EOF
Команды для инициализации и пуша:

Копировать
go mod init github.com/<твой-логин>/myapp
git init
git add .
git commit -m "initial commit"
git remote add origin https://github.com/<твой-логин>/myapp.git
git push -u origin main
После пуша открой вкладку Actions в репозитории и убедись, что workflow прошёл зелёным.


Во вкладке Actions на GitHub видно зелёный чекмарк для шагов Build и Test
отметить
Задача 2. Добавить линтер golangci-lint в пайплайн
Расширь существующий ci.yml шагом запуска golangci-lint.
Линтер проверяет стиль кода - без него пулл-реквесты часто содержат неочевидные проблемы.

Добавь новый job в ci.yml после блока build::

Копировать
cat >> .github/workflows/ci.yml << 'EOF'

  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'

      - name: Run golangci-lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.59
EOF
Чтобы убедиться, что линтер что-то ловит, добавь в main.go неиспользуемую переменную (это вызовет ошибку компиляции в Go, поэтому вместо этого оставь неиспользуемый импорт через _).
Либо закоммить как есть и посмотреть, что lint job тоже зеленеет.

Копировать
git add .github/workflows/ci.yml
git commit -m "add lint job"
git push

В Actions появился job lint, он прошёл без ошибок
отметить
Задача 3. Настроить кэширование зависимостей
Без кэша каждый запуск CI скачивает все зависимости заново - это медленно.
Добавь кэширование модульного кэша Go.

Измени шаг Setup Go в job build в файле .github/workflows/ci.yml - action setup-go@v5 умеет кэшировать автоматически при наличии go.sum:

Копировать
# Текущий блок setup-go в job build выглядит так:
#   - name: Setup Go
#     uses: actions/setup-go@v5
#     with:
#       go-version: '1.22'
#
# Замени его на:
Копировать
cat > .github/workflows/ci.yml << 'EOF'
name: CI

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Build
        run: go build ./...

      - name: Test
        run: go test ./...

  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Run golangci-lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.59
EOF
Копировать
git add .github/workflows/ci.yml
git commit -m "enable go module cache"
git push
Открой детали второго запуска workflow и найди шаг Setup Go - там должна появиться строка вроде Cache restored from key:....


В логах шага Setup Go второго запуска видно восстановление кэша
отметить
Задача 4. Добавить сборку Docker-образа в CI
Расширь пайплайн шагом, который собирает Docker-образ приложения.
Это стандартная часть CD-части пайплайна.

Создай Dockerfile в корне проекта:

Копировать
cat > Dockerfile << 'EOF'
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod ./
RUN go mod download
COPY . .
RUN go build -o myapp .

FROM alpine:3.19
WORKDIR /app
COPY --from=builder /app/myapp .
CMD ["./myapp"]
EOF
Добавь job docker в ci.yml:

Копировать
# Добавь в конец файла .github/workflows/ci.yml следующий блок:
Копировать
cat >> .github/workflows/ci.yml << 'EOF'

  docker:
    runs-on: ubuntu-latest
    needs: [build, lint]
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Build Docker image
        run: docker build -t myapp:ci .
EOF
Ключевое слово needs означает: job docker запустится только если build и lint оба прошли успешно.
Это защита от сборки образа из сломанного кода.

Копировать
git add Dockerfile .github/workflows/ci.yml
git commit -m "add docker build job"
git push

Job docker в Actions завершился успешно и запускался после build и lint
отметить
Задача 5. Добавить проверку покрытия тестами
Настрой вывод процента покрытия тестами в CI.
Это помогает отслеживать, что новый код не остаётся без тестов.

Замени шаг Test в job build на расширенную версию с флагом -coverprofile:

Копировать
cat > .github/workflows/ci.yml << 'EOF'
name: CI

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Build
        run: go build ./...

      - name: Test with coverage
        run: go test -coverprofile=coverage.out ./...

      - name: Show coverage
        run: go tool cover -func=coverage.out

  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Run golangci-lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.59

  docker:
    runs-on: ubuntu-latest
    needs: [build, lint]
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Build Docker image
        run: docker build -t myapp:ci .
EOF
Копировать
git add .github/workflows/ci.yml
git commit -m "add coverage report"
git push
В логах шага Show coverage увидишь таблицу вида:

Копировать
github.com/.../main.go:7:    Add    100.0%
total:                        (statements)  100.0%
